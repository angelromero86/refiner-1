# refiner

Git code-review TUI: partial-line staging plus review threads. Bun + OpenTUI
(`@opentui/core`, native Zig core). Ported from eleview (Go + bubbletea).

Run it with `bun run src/index.ts`; `bun test` and `bun run typecheck` before
committing.

## Load-bearing invariants

**`src/diff.ts` is the contract.** `buildPartialPatch` output goes straight into
`git apply --cached`, so a subtle change there corrupts the user's index.
`test/diff.test.ts` pins it byte-for-byte against fixtures generated by the original
Go implementation (14 real diffs × 8 include-set strategies), and
`test/staging.integration.test.ts` runs the real thing against throwaway git repos.
Never "clean up" that file without both suites green.

In particular: `\ No newline at end of file` markers must survive the round-trip.
A dropped marker makes git reject the patch because context lengths stop matching
HEAD. `Line.noNewline` exists only for this.

**Index spaces are not interchangeable.** Staging always works in *unified* index
space. Split rows map back via `oldSrcIdx`/`newSrcIdx`; "current" (NORMAL) rows map
back via `currentIdx`. Mixing them silently stages the wrong lines.

**Staging is reset-then-apply.** The patch describes the COMPLETE desired staged
set against HEAD, never a delta — `src/staging.ts` resets the file's index entry
first. That is what keeps repeated partial stages from drifting. For a file with
no blob in HEAD the reset REMOVES the entry, and that is a precondition, not a
convenience: `git apply --cached` rejects a `new file mode` patch with `already
exists in index` when the entry is still there.

**The patch header's shape comes from git, never from the lines.** A file absent
from HEAD needs `new file mode <mode>` · `--- /dev/null`; the classic
`--- a/<path>` fails it with `does not exist in index`. `buildPartialPatch`
cannot work that out for itself — a file whose HEAD blob is EMPTY produces a
byte-identical filtered `Line[]` (all Add) and needs the opposite header — so the
verdict is read off git's own header by `creationMode()` before
`filterContentLines` discards it, cached as `RenderedDiff.createMode` and handed
back in `buildPartialPatch`'s optional `PatchHeader`. Two rules there: the
argument is opt-in, because omitting it must stay byte-identical to the Go
fixtures in `test/diff.test.ts` (`real7.diff` IS a creation whose golden patches
use the classic form, and the generator lives in the Go project); and the mode is
copied, never hard-coded, or an executable silently loses its `+x` bit.

The deletion end is the same rule mirrored, and it bites harder because it fails
QUIETLY: a file gone from the working tree whose every line is selected needs
`deleted file mode <mode>` · `+++ /dev/null`, and without it git accepts
`+++ b/<path>` with `+1,0`, exits 0, and leaves the EMPTY blob in the index — so
the commit writes an empty file where the user asked for none. Here too the lines
cannot decide: TRUNCATING a file to zero bytes yields a byte-identical filtered
`Line[]` (all Del, same `@@ -1,N +0,0 @@`) and must keep the classic header — the
golden fixture `alldel.txt.diff` is exactly that case, so an inferential fix
would move it. `deletionMode()` reads the verdict, `RenderedDiff.deleteMode`
caches it, and `newCount === 0` gates it so a PARTIAL selection over a deleted
file stays an ordinary modification. Dropping `deleted file mode` while keeping
`+++ /dev/null` is not a lighter version of the fix: git then also writes a bogus
`dev/null` entry. And the mode matters more than on the creation side — a symlink
announced as `100644` is rejected outright with `wrong type`.

**Staging is queued, and decided synchronously.** One operation takes ~21 ms;
autorepeat is ~30 ms. `toggleStaged`/`toggleFullStage` therefore resolve the
cursor, decide the direction and record the result in `app.stagingIntent`
*during* the key dispatch, then hand a job to a serial queue — never `void`
straight at git. Two operations in flight interleave `unstage₁, unstage₂,
apply₂, apply₁` and lose a line. Two decisions from `app.staged` — git's answer
to the previous press, a reload behind — do the same thing silently, because
the second one's complete-desired-set patch describes the first one's line as
unstaged. Read the staged set through `app.stagedFor(path)` (intent, then git)
and never re-derive it from `app.staged`. Coalescing pending jobs by path is
only safe because of the invariant above.

**refiner always runs from the repo root.** `main()` calls `enterRepoRoot()`
(`src/git.ts`) before anything touches the repo, and everything downstream assumes
it. Domain paths — `ChangedFile.path`, `StoredThread.file`, the headers inside the
patch fed to `git apply --cached` — are root-relative and never absolute; making
them absolute would break the patch, the `app.cache` keys and the store contract
with the VSCode extension all at once. git's pathspecs and `Bun.file()` resolve
against the cwd instead, and git answers a pathspec that matches nothing with exit
0 and no output, so from a subdirectory every diff comes out blank and staging
quietly does nothing. At the edge of a child process that does NOT inherit our cwd
— the tmux/zellij editor popup — compose the absolute path right there, from
`app.root`. `test/subdir.test.ts` runs the real pipeline from a subdirectory.

**A `ChangedFile` is exactly one path.** The tree splits `path` on `/`, `app.cache`
and `app.staged` key on it, `stageFile`/`unstageFile` hand it to git as a pathspec
and `buildPartialPatch` writes it into the patch header. A rename is the one thing
git reports over two paths, so both queries in `loadChangedFiles` pass
`--no-renames` and the pair arrives as an ordinary `D` plus an ordinary `A`. Drop
the flag from either one — porcelain and `--name-status` are parsed by different
functions — and `RM old -> new` comes back as the literal path `"old -> new"`:
blank diff, `fatal: pathspec` on stage, a silent no-op on unstage (`git reset`
exits 0 on an unmatched pathspec), and a phantom `src/a.ts -> src` directory.
Nothing is lost in the panel, because `loadDiff` restricts the diff to one path and
git therefore never emits rename headers anyway. `test/renames.test.ts` pins it.

**`.refiner/comments.json` is shared** with the Refiner VSCode extension and with
agents. Preserve fields you don't understand — `anchor`, which the extension
maintains for drift tracking, unknown keys inside a thread, and unknown keys at the
ROOT — and keep the serialization at `JSON.stringify(data, null, 2) + '\n'` so the
two tools don't fight over whitespace. That is why parsed objects are mutated in
place and never rebuilt field by field, the root object included.
`test/comments.test.ts` guards all of it.

Because every save rewrites the whole file, **a `Store` that never managed to read
its file never writes it**. `Store.load()` throws on malformed JSON, and that only
protects anyone if the caller stops there — an empty-but-writable fallback store
was how a half-written file from the extension, or an agent killed mid-write,
became a file with one thread in it. So the rule lives in the store, not in its
callers: `loadOrReadOnly()` marks the fallback, `markUnreadable()` poisons a store
whose file broke under it, and `save()` rejects before touching `lastSyncedText`
(a value describing a write that never happened would make the watcher mistake the
real file for our own echo). A missing or empty file is an ordinary new repo and
stays writable. Recovery is a successful `load()` — nothing un-poisons a store.
The header, not the error banner, carries the read-only state: the banner replaces
the whole tree pane and `r` clears it, so a latched warning was one keystroke from
being dismissed while the store was still unwritable.

**We are never the only writer, and the dangerous window is the whole session.**
An agent replying while the reviewer composes used to be erased by that comment: a
save wrote a copy of the file read at startup. So `save()` re-reads first, and when
the bytes moved since `lastSyncedText` it replays the local mutation log onto the
DISK copy instead of overwriting it. Three things hold that up. The log is keyed by
**id, never index** — an index means nothing after somebody else's insert, which is
also why `Store` resolves the caller's comment index to an id at mutation time.
Saves are serialized through `writeChain`, because `threads-ui.ts` fires them with
`void` and two merges onto the same base clobber each other. And unparseable bytes
are still a refusal, not a base: that is the same `markUnreadable()` poison, so the
merge can never flatten a write in progress. Conflicts the format cannot express —
a reply to a thread the other client deleted, an edit to a comment they also
edited — are counted in the `SaveReport` and reach the banner; silence there would
be this bug again in miniature.

Two consequences elsewhere. **The modal is re-anchored by id after a merge**
(`ThreadModal.threadId`): its `threadIdx` indexes an array the merge has just
rebuilt, and `d`/`D` read the thread straight out of it, so a stale index deletes
somebody else's thread. And **the file is replaced by rename, not truncated** —
`Bun.write()` over an existing path truncates in place, which serves concurrent
readers a half-written file, i.e. manufactures the unreadable-store case above for
the process next door. The watcher watches the `.refiner/` directory, not the file,
partly for that reason; it ignores the `comments.json.<pid>.<n>.tmp` we rename from.

## OpenTUI specifics that bit us

- **Global key handlers run before focused renderables and can `preventDefault()`,
  but only synchronously.** `src/dispatch.ts` therefore decides synchronously and
  fires git/store I/O without awaiting. Making a handler `async` means
  `preventDefault()` lands after dispatch, and keys leak into (or never reach) the
  focused text widget.
- **Loads carry a generation, so a keypress can start one without awaiting it.**
  `App.loadGen` is bumped synchronously by `clearCaches()` — the only bumper —
  and every async load captures it on its first line and writes nothing shared
  once it is no longer current. Two `tab` presses inside git's latency used to
  leave the header saying CHANGES while the tree listed the whole repo, because
  `loadAllFiles` runs two git commands to `loadChangedFiles`' one and therefore
  landed last. A stale load must not set `err`, must not consume
  `pendingNavLine`, and must not refill a cache that was just dropped. The
  precondition is bump-then-load: every bump is immediately followed by a load
  that repopulates the screen, which is why `onResize` — reachable with nothing
  selected — clears `cache` by hand instead. Note this is the opposite treatment
  to staging above, on purpose: a reload is a read, where the newest intent
  invalidates the older one, while a dropped staging press loses work.
- **Focusing a hidden renderable is a silent no-op.** Widget focus is derived from
  state in `View.syncWidgetFocus()`, after visibility is settled for the frame.
  Don't call `focus()` from the app layer.
- **Overlays need an explicit `backgroundColor`.** Boxes default to transparent, so
  a modal without a fill shows the diff straight through its text.
- **`wrapMode: 'none'` everywhere.** Rows are pre-padded to exact column counts; a
  wrapped row would shift every row below it instead of failing locally.
- Widths come from `Bun.stringWidth` (`src/text.ts`), not `String.length` — the Go
  original measured bytes in `fit()` and misaligned any row with non-ASCII.

## Themes

`src/theme.ts` owns the built-in palettes (`BUILTIN_THEMES`: gruvbox-dark,
gruvbox-light, vesper) and `t` swaps between them at runtime. Each entry is a
WHOLE `Theme`, never a patch over the default — a light theme moves every knob,
and `buildSyntax` expands eleven roles into the full capture-group table so a new
palette cannot ship half a map (the `markup.*` groups went missing exactly once
already, and markdown rendered bare for it).

Two things decide which palette is live, and they are kept apart on purpose.
config.toml contributes a base NAME (`theme = "vesper"`) plus individual color
keys, and those keys are held as `Config.themeOverrides` rather than baked into
the resolved theme — they are the user's explicit instruction, so `resolveTheme`
re-applies them over whichever base the picker lands on. state.json contributes
the picker's last choice, which outranks the file because pressing `t` is the
more recent instruction; `App.themeChoice` is written ONLY by `chooseTheme`, so
saving any other preference can't latch config.toml's theme into state.json and
shadow the file forever. An unknown name anywhere degrades to the default.

Everything reads `S` while drawing, so a swap needs nothing but a render — except
the colors that live ON renderables built once (pane fills, overlay borders and
backgrounds, the two text widgets). `App.themeEpoch` is bumped by `setTheme` and
the view restamps those in `applyPalette()` when it changes, rather than
reassigning them every frame and marking each one dirty.

## Syntax highlighting

`src/syntax.ts` highlights the diff as **two whole documents** (post-change =
context+additions, pre-change = context+deletions) and each row looks up its runs by
line number. Per-row parsing would produce nonsense for anything spanning lines.

Three things must stay in lockstep or the colors land on the wrong characters:

- **Tabs are expanded before highlighting**, exactly as the renderers expand them.
  A raw tab in the document but `    ` on screen offsets every later column.
- **Tree-sitter offsets are UTF-16 code units**, not bytes — verified against its own
  parser. So the runs can slice the JS string directly. Don't "fix" this to bytes.
- **Runs are string indices, not display columns.** Slice text by them; never use
  them for padding math. Width still comes from `Bun.stringWidth`.

Overlapping captures are normal (tree-sitter emits `variable`, then `type`, then
`constant` for one span). They're painted into a per-column array so the most
specific wins, then collapsed back into runs.

**Not every capture is a color.** The queries come from nvim-treesitter, which
also marks up editor features we don't implement: `spell`/`nospell` for the spell
checker, `conceal` for delimiters an editor would hide, `none` for "explicitly
nothing". They arrive AFTER the visual capture covering the same span, so the
last-wins painter buried the real one under them — a markdown code span was
captured as `markup.raw` and then overwritten by `nospell`, which no theme maps,
so it rendered as plain text. `NON_VISUAL_GROUPS` drops them. This is most of why
markdown used to look unhighlighted; the other half was the theme having no
`markup.*` colors at all, only the `title`/`emphasis`/`literal`/`reference`/`uri`
names the Go original used, which no tree-sitter grammar has ever emitted.

**Embedded languages are our own second pass, not a tree-sitter injection.** An
Angular component's real content is the HTML in its `template:` string, and the
whole thing used to render as one flat string. `findInjections` (`src/syntax.ts`)
scans a typescript/javascript document for template literals that hold another
language — the `template:`/`styles:` keys of `@Component`, and lit-html's `html`
/`css` tags — highlights each with that grammar, and paints the result over a
CLEARED span so the host's one big `string` capture doesn't show through.
OpenTUI's client does support injections, but it picks the language off the
captured NODE TYPE, and Angular's HTML and CSS are both a plain `template_string`
— one mapping cannot tell them apart, which is why the scan is ours.

Three things keep a wrong guess cheap. A literal is claimed only when the token
before it says so, so a backtick the scanner doesn't model (a regex literal
holding one) costs a missed region, never a wrong one. The `${…}` substitutions
are held back as `holes` and keep the host's colors — they are host code, and
lit-html templates are full of them. And a region must be TERMINATED within one
hunk: the document is diff context rather than the file, so an unclosed template
would otherwise swallow unrelated code pasted after it by the next hunk and paint
it as markup. That is what `Document.gaps` is for — `documentFor` records where
the line numbers jump, and nothing may span one.

**We ship our own grammars.** @opentui/core bundles four — typescript,
javascript, markdown, zig — so everything else fell through to flat diff colors.
`assets/parsers/<filetype>/` adds json, toml, css, scss, html and xml as a
`parser.wasm` plus one `highlights.scm`, handed to the client at startup through
`addFiletypeParser`, which takes local paths. Nothing is fetched at runtime: a
git TUI opening network connections on its own is not a feature.

Three things about that. The artifacts are committed but `scripts/fetch-parsers.ts`
regenerates them, and it is where each one's origin and license lives — grammars
come from their own release pages so they match the queries written against them,
except SCSS, which publishes no wasm and is compiled from its npm tarball with
the tree-sitter CLI. `parserRoot()` resolves from the module's own location, never
the cwd, because refiner runs from the *user's* repo root — and a compiled binary
resolves nothing that way at all, so the sidecar copy `bun run build` writes is
its only route. And the failure mode is silence in every direction: an unmapped
extension, a missing asset and a query that won't compile against its grammar all
look the same on screen, like a file nobody colored. `test/syntax.test.ts` pins
the mapping, the assets and the build step for that reason.

`configureAssetRoot()` exists because OpenTUI resolves its tree-sitter assets
relative to its own module URL, which under Bun is the global install cache where
the `web-tree-sitter` peer dep isn't reachable. Setting `OTUI_ASSET_ROOT` to a real
node_modules (or the shipped sidecar) fixes it. A compiled binary additionally can't
spawn the parser worker from Bun's virtual filesystem, which is why `bun run build`
emits `dist/refiner-assets/` — ship it alongside the binary or highlighting silently
switches off (by design: `highlightDiff` never throws).

## Vocabulary

A **thread** is anchored to `(file, line range)`, carries `status`, and contains one
or more **comments**. Keep these words apart in identifiers and in anything the user
reads — an earlier pass had the header counting threads while labelling them
"comments", and the thread modal calling comments "messages".

Rules: `store.threads` is the list of threads (the field is `app.store`, never
`app.threads`, so `store.threads` reads correctly). `lineHasThread` asks about
anchors; the `thread`/`thread_label` theme colors paint the "a thread is anchored
here" cue. The word "message" is not used anywhere.

## Keymap

`src/keymap.ts` is the single source of truth for the `k` overlay. There is no
footer: it cost a permanent row to repeat the same hints, so the keys moved behind
`k` (aliased `?`) and the header advertises it. The diff pane's line readout rides
its title row (see Layout). The tree deliberately has no counterpart: its cursor
row is on screen already, so a `3/14` index only restated it.

If you add a binding in `dispatch.ts`, add it to `keymap.ts` too — nothing else
surfaces it, so an unlisted key is an undiscoverable key.

`j`/`k` are deliberately not navigation aliases any more; `k` is the help key.

`q` and `esc` open a quit confirmation rather than exiting outright; `⌃c` still
exits immediately from anywhere, which is the deliberate escape hatch. Nothing is
lost on quit — threads are written on every edit, staging lives in git — so the
confirmation guards against the fat-finger, not against data loss.

## External processes

`src/externals.ts` has three paths: a tmux `display-popup`, a zellij floating pane,
or suspend-the-renderer. Only the last is full-screen, and that is not a choice —
without a multiplexer nothing can hand a child process a sub-rectangle of the
terminal. Doing it ourselves would mean a PTY (`Bun.Terminal`, which Bun does
provide) plus a VT emulator to paint the child's output, plus a prefix key to
arbitrate keystrokes. That is rebuilding tmux; don't.

In the multiplexer paths the child must NOT inherit our stdio — the renderer still
owns the terminal, so a tmux error message would be painted straight over the UI.
Its output is captured and routed to the error banner instead.

**`loadFiles()` must not clear `app.err`.** Staging and external processes record an
error and then refresh; clearing on a successful reload wiped the error they had
just set, which is why failures used to vanish silently. Only the explicit `r`
binding clears the banner.

## Layout

`src/app.ts` holds all state and the geometry helpers; `src/view.ts` draws and owns
the renderable tree; `src/dispatch.ts` routes keys through `src/keys.ts`, which
normalizes OpenTUI events into the compact strings ("shift+up", "alt+enter", " ")
the handlers switch on. Feature logic lives in `staging.ts`, `threads-ui.ts` and
`finder.ts` as functions taking the app — mirroring the Go methods they came from.

**The frame is four rows, one column and two junctions.** Row 0 is the header —
repo · source on the left, the counts and `k keys` on the right. Row 1 is a rule
across the full width. Row 2 is the title row, whose halves describe the pane under
each: CHANGES/ALL over the tree, path + view mode + line readout over the diff.
Under it the vertical rule divides tree from diff, meeting the horizontal one in a
`┬`. Row 3 is a second, lighter rule, closing each title off from the pane it names
— without it the first file and the first line of code sit flush under a label the
same size as they are, and the eye reads the title as the first row of the list.
The panes are borderless, so the height math is one step: `paneInnerHeight()` is
`height - 4`, and `diffPanelWidth()` only has to give the vertical rule back its
column. What this replaced
was a boxed header plus two rounded pane borders — five rows and eight columns of
chrome — carrying labels that sat on the wrong pane anyway: the file-list mode and
the view mode were in the header, away from the pane each one describes and from
the key that changes it. Overlays keep their borders; they float over the panes and
need the edge.

The rules are one family — `│ ─ ┬ ┼`, light box-drawing — in the same muted tone as
the `│` the diff already draws between its line numbers and its code. They carry
exactly two weights, and which one a rule gets is a claim about what it divides:
the rules between the panes are `paneRule`; the one between a pane and its own
title is `paneRuleSoft`, half way from that tone to the background. A third weight
is how a frame starts growing back.

Both horizontal rules are drawn full-bleed by `buildRuleRow` — no padding, and off
`treePanelWidth()` rather than the panes' own boxes — because each has to land its
junction on the exact column the vertical rule occupies. They differ only there:
`┬` under the header, where the divide starts, and `┼` under the titles, which the
divide passes straight through. The junction always takes the strong tone, so the
vertical rule reads as continuous from the `┬` to the bottom of the screen while
the light rule crosses behind it. A plain `│` there instead leaves the light rule
visibly broken on both sides of it.

The title row is a flex row of the same three widths as the panes below it — tree
box, rule, diff box — and not one full-width string with the columns worked out by
hand. It has to stay aligned with pane widths that move under `[`/`]`, the tree
auto-hide and every resize, and letting the layout engine do that is the difference
between "aligned" and "aligned until someone edits a padding".

**Focus moves the text, never the furniture.** The focused pane's title takes
`focus` and bold, and the tree's cursor row stays painted while the tree is idle,
at the derived `cursorBgIdle` — half way to the background — instead of vanishing.
That second one is not decoration: a lit border used to say "this pane is asleep",
and without one a tree that also forgot where the cursor was left nothing to come
back to. The rules are deliberately NOT part of this. A pass that had the vertical
rule lean toward the focused pane (`▌`/`▐`) read as the layout twitching on every
`←`/`→`, and the half block was twice the weight of every other line on screen.
The diff pane still drops its cursor row and selection when idle
(`RowState.focused`, gated inside all three renderers in `render.ts`); giving it
the tree's treatment means an idle variant of every `CursorRowStyles` set, which is
a bigger change than it looks.

**A folder's name is colored by what it owes; its glyph is not.** The icon keeps
the accent in every state — it is what says "folder" at a glance, and a tree
whose shape changes color as you stage is harder to read, not easier. The NAME
is the variable, and `dirState` (`src/tree.ts`) spends it on the work left under
the folder: `dir` while any descendant is unstaged, `dirStaged` once
everything that changed is in the index, and plain `text` — the file style —
when nothing under it changed at all. The distinction that makes it work is
`hasUnstagedChanges` vs `!fullyStaged`: they differ precisely on an UNCHANGED
file, which only ALL mode produces, and treating those as "not staged yet" is
what used to paint every folder in the repo as if it needed attention. Same
reason the walk reads `child.file` instead of `App.findFile(child.path)` — that
lookup is a linear scan over every file in the repo, once per descendant, on
every frame. `test/tree.test.ts` pins the three states.

**Every jump that moves the diff pane goes through `revealPath`.** The mode
toggle, the finder (`⌃p`) and `jumpToThread` all point the right pane at a file
without the tree cursor having walked there, and each one used to park the
cursor only *if the row happened to be visible* — which in ALL mode it usually
is not, because entering ALL folds the repo down to its folders. So the tree
kept pointing at where you were while the diff showed where you went.
`App.revealPath` opens the folders on the way down, re-flattens, and parks the
cursor; the pane scrolls because its window is derived from the cursor. Two
things it must keep: only the ancestors open (revealing a file is not a back
door to expanding the repo), and the caller must be past its generation guard,
because `collapsed` answers for whatever mode is active when it runs — the same
trap `collapseAllButPath` documents. A file the target mode doesn't list is not
a case to fix here: `toggleFileMode` clears the selection first, and
`revealPath('')` is a no-op.

**The scrollbar column only exists when it can scroll.** `buildContent` reserves
the last column for it when `activeRowCount() > h` and hands it to the code
otherwise — a diff that fits shows its change bands as the diff itself, so the
minimap was drawing a second copy of what was already on screen and charging a
column for it.
